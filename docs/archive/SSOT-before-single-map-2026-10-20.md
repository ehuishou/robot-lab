## S4. 技术路线决策框架

### S4.1 方案比较与建议

以下是针对本项目的架构取舍，不是性能实测或“换引擎必然变好”的保证。

| 路线 | 计划保留 | 需要重做 | 主要风险 | 当前建议 |
|---|---|---|---|---|
| A. 继续 Phaser | 当前场景组织、部分绘制逻辑 | 启动/输入/状态、完整 UI、美术资源、物理与目标闭环 | 在旧场景耦合上继续堆叠；仍需投入正式美术 | 作为保底，不再仅靠加网格/光效修饰 |
| B. Three.js 2.5D + DOM UI | 经测试的领域数据与规则、任务 ID、可迁移存档 | 场景表现、机器人视图、页面布局、生命周期、输入桥接 | 迁移期间双入口、资源/坐标约定和 GPU 兼容性需要管理 | **首选提案：先做单关样板，由用户确认效果再扩展** |
| C. 完整自由 3D | 少量领域规则 | 自由相机、3D 导航与碰撞、大量模型和关卡设计 | 范围失控，偏离当前横向运输玩法 | 本轮不纳入 |

选择 B 的目的是重新建立空间层次、材质/光照和网页布局体系，而不是用引擎替换代替缺陷修复。**Three.js 样板已在恢复开发授权范围内，R2-A/B 已实施；全量迁移须通过 R3 用户视觉和操作认可。** 不反复请求一般开发许可，也不绕过全量迁移门槛。

### S4.2 2.5D 的明确边界

- 玩法仍为横向行驶、模块配置、搬运/清障；机器人运动限定在路线平面，不增加自由漫游。
- 计划采用可表现前后层次的三维场景和固定斜侧视相机；相机跟随/缩放有边界，不让玩家自由旋转到看不清路线的位置。
- 世界坐标统一为 X 前进、Y 向上、Z 景深；新领域单位拟统一为米、秒、千克。旧像素距离只在迁移适配层换算，不能直接沿用旧常量。
- UI 采用独立 HTML/CSS 层；菜单、配置、目标、按钮、结算不放进世界相机。世界层负责机器人、地形、货物、装饰与效果。
- 首个样板优先稳定的地面跟随/受约束车辆运动，不直接移植已发散的射线悬挂。悬挂细节先作为视觉反馈；真实弹跳/腾空另经数值验收后再引入。
- Three.js 版本、加载器、构建依赖与浏览器最低要求留到后续实施前核对官方文档并锁定；本轮不假定已安装，不填写未经验证的版本/API。

## S5. 目标架构、数据与交互契约

### S5.1 职责分层（样板已有应用、领域、内容、渲染、DOM界面与输入实现；全量架构仍待迁移）

| 层 / 建议目录 | 职责与输入输出 | 禁止事项 |
|---|---|---|
| `src/app/` | 应用状态机、路由/入口、初始化、错误边界、全局生命周期 | 不把任务规则散落在页面点击事件中 |
| `src/domain/config/` | 配置完整性、能力/容量/成本约束、派生参数；输出结构化诊断 | 不依赖 DOM 或 Three.js，不用名称子串判断能力 |
| `src/domain/mission/` | 任务会话、目标/限制、事件、成功失败及结算；生成只读快照 | 不让多个系统各自宣告任务成功 |
| `src/domain/simulation/` | 统一单位下的运动、能耗、载重、地形采样、碰撞反馈 | 不读屏幕像素，不直接修改模型或 UI |
| `src/content/` | 模块、任务、物品、布局、关卡主题、素材清单与校验 | 不允许描述、目标、布局各自表达不同任务 |
| `src/render/` | Renderer 生命周期、CameraRig、RobotView、TerrainView、Item/ObstacleView、灯光/效果 | 不拥有第二份权威能源、目标或载重状态 |
| `src/ui/` | DOM 页面、组件、设计令牌、响应式布局、焦点及触控可访问性 | 不通过相机坐标定位操作按钮 |
| `src/input/` | 键盘和 pointer 状态集合，生成统一 DrivingIntent | 不让释放一个输入源清掉其他仍按住的输入源 |
| `src/services/` | 资源加载、存档、音频、诊断、构建身份 | 不静默吞掉资源错误，不静默重置旧存档 |

数据流固定为：**输入意图 → 会话/模拟 → 领域事件与状态快照 → 世界视图和 DOM UI**。渲染动画允许插值，但不能反向修改权威任务状态。

样板当前由 `VisualPreviewApp`、`DrivingSessionController`、`FixedStepClock`、领域会话与模拟、`PreviewRenderer` 和 `BrowserDrivingInput` 连接；DOM模板和状态更新仍在应用层，样式位于 `src/ui/preview.css`。独立存档由 `src/app/PreviewSave.ts` 实现，尚未统一为上表建议的 `src/services/`；不将目标目录结构当作已经完成的全量重构。

### S5.2 必须统一的数据契约

| 契约 | 必备内容 | 校验重点 |
|---|---|---|
| ModuleDefinition | 稳定 ID、类别、能力集合、成本/质量、载重与派生属性、视图资产 ID | 同一配置切换同步改变参数和可见模块；能力/容量不能互相冒充 |
| MissionDefinition | ID、环境主题、地形、确定性布局、完成目标、硬限制、奖励条件、推荐合法配置 | 任务有实际目标对象和卸货点；所需能力可由合法组合提供 |
| TerrainProfile | 长度、高度采样、坡度/曲率限制、出生/卸货平台 | 渲染、运动、障碍、拾取位置读取同一采样；平地确实平坦 |
| SessionState | 唯一会话 ID、阶段、配置快照、位置/速度、时间、能源、载重、货物、目标、碰撞 | 重新开始生成全新状态；旧事件不能污染新会话 |
| DomainEvent | 会话 ID、时刻、事件类型、对象 ID、必要载荷 | 拾取/卸货/清障只计一次，暂停时不推进时间与目标 |
| RenderSnapshot | 位姿、模块外观、可见对象及反馈事件 | 只读；表现对象销毁不等于业务对象被完成 |
| AssetManifest | 稳定 ID、类型、路径/生成方式、尺寸或尺度、必要性、降级方式、授权记录 | 禁止把占位资源标成正式美术；缺少必要资源有明确错误页 |

### S5.3 规则框架

- 配置验证必须同时返回完整性、缺少能力、容量不足和预算/重量问题；配置页、开始按钮和会话初始化使用同一结果，避免只显示警告却仍能启动。
- 样板已将电池容量上限与独立 `maxEnergyConsumedUnits` 消耗预算分开，01不新增消耗预算；其余关卡迁移时先澄清旧 `maxEnergy` 字段语义，UI名称与算法必须一致。
- 搬运校验：实际携带总质量 + 新货物质量不得超过有效容量；能力满足但容量不足应给出独立提示。卸货后质量与运动参数同时刷新。
- 完成目标是抵达、搬运、收集、清障等有限事件；时间和碰撞上限是全过程限制，不要求其事件进度达到上限才能成功。
- 每个固定步建议顺序：应用输入/交互 → 更新模拟与耗能/时间 → 检查硬失败 → 检查完成目标 → 冻结结算；同一时刻只产生一种结果。
- 初始边界约定：时间等于上限仍合法，超过才失败；碰撞等于上限仍合法；奖励条件在最终成功时结算。该约定要写入测试，不以帧率决定结果。
- 样板空电量冻结速度并结算能源耗尽，不允许同一步借惯性抵达判成功；碰撞减速、限速必须由模拟层写回速度，不只在 HUD 提示。
- 退出/重开须释放所有输入、订阅、计时器、音频和渲染资源。监听与动画不得跨会话累积；页面隐藏时暂停推进，恢复不补算无限步数。
- 失焦、pointercancel、抬手在按钮外、多指并按、键盘与触屏混用均纳入输入协议；菜单打开时不让操作穿透到车辆。

### S5.4 生命周期与故障表现

计划流程：启动诊断 → 加载 → 主菜单 → 配置/选关 → 游玩 ↔ 暂停 → 成功或失败结算 → 重开/返回。每个流程明确进入、退出和清理责任。

- 启动页展示加载进度和构建身份；加载失败、WebGL 不可用、上下文丢失时展示可读提示及重试入口，不停在空白画布。
- 浏览器 resize 与 DPR 变化分别更新世界画布和 UI 布局；相机不裁掉出生位置、机器人或目标区域。
- 模型/纹理/几何体/材质/音频的所有权登记在会话或全局服务中，结束时按所有权释放；不得凭场景看起来消失就认定资源释放完成。
- 存档增加版本和迁移策略；损坏数据提供恢复/重置选项，升级失败保留旧数据；重构预览不默认覆盖旧版进度。

本轮将“三个固定的任务目标和预算”解释为三套固定挑战，每档一套目标组合和预算，不随机抽任务、不要求逐级解锁。下列具体预算、货物安排和评分常数是根据现有模块提出的首版建议值，并非用户指定的数字。可在开发实测后统一调整；同一已发布规则版本内保持固定。

状态：三档任务数据、选择入口、预算校验、开局快照、正式计分、版本化成绩存档与测试隔离已实现。首版建议值经正常模式驾驶验证后采用为 challenge-v1，未改模块价格；本地构建与证据见 S9.7。本轮开发未部署服务器，自动化手机模拟不替代真实设备验收。

### S9.2 固定任务与预算（challenge-v1）

预算单位为游戏成本点，与模块 cost 同口径。

| 难度 / ID | 预算 B | 必需任务 | 固定路线 | 难度系数 D |
|---|---:|---|---|---:|
| 简单 / challenge_easy | 600 | 40m装载1件8kg轻货，并交付 | 100m平地；93–97m卸货区；100m终点 | 1 |
| 普通 / challenge_normal | 500 | 30m、60m各装载1件8kg轻货，两件均交付 | 100m连续缓坡；93–97m卸货区；100m终点 | 2 |
| 困难 / challenge_hard | 450 | 30m装载1件20kg重货、60m装载1件8kg轻货，两件均交付 | 与普通相同的100m缓坡；93–97m卸货区；100m终点 | 3 |

- 每件货物有独立 ID；必须在指定区域有效卸货，拾取、经过和重复卸货不算交付。
- 允许分批运输。困难总货重28kg高于现有机械臂25kg容量，需要至少两趟；配置校验只要求能单独搬起最重的20kg货物，不错误地要求同时承载28kg。实际拾取始终校验累计载重。
- 按真实能力与容量验证，不锁定模块 ID，不要求同一工具槽安装互斥工具，不以测试模式的万能工具证明正常模式可行。
- 普通/困难复用现有缓坡形状，在30m、60m新增平缓装载平台并连续过渡；最大坡度遵循现行10°上限。路线、平台、货物、补能位置均固定，显示与交互使用同一地形高度。
- 建议三档统一180秒上限；20m、80m各一个20单位补能点，每个只能领取一次。正常能源消耗、能源耗尽和倒地失败保留。时间不作为难度倍率或加分项，困难往返是否能在时限内完成必须实测。
- 首版沿用整机质量上限80kg（含20kg基础质量，不含货物）、电池容量上限100单位和完整五槽要求；预算合法不等于能力、重量、载重也合法。
- 新挑战不放置得分星标或宝箱，补能仅补充能源。旧样板可留在开发预览，不作为第四档正式挑战。

静态初查（2026-10-17）：按当前模块价格、质量/电池约束及能力枚举，简单41套、普通22套、困难4套配置合法，最低成本分别340、340、370。普通按可同时承载16kg筛选，困难按单件20kg筛选。该结果不证明路线、能源或时限可通关。困难预算下当前有轮式/履带方案，四足超预算，这是建议数值的已知取舍，不暗改模块价格。正式开放前每档至少两套不同配置实际通关。

### S9.3 难度选择、预算和会话

1. 三档同时开放，首次默认简单，之后记住上次选择。卡片只显示难度、目标摘要和预算；选中后进入组装。
2. 组装显示“预算 / 已用 / 剩余”，换模块实时更新。切难度保留配置并重新校验，不悄悄更换配件；超预算或缺能力禁止开始并解释原因。
3. 配置成本 C 为五件已装备模块的正常目录价格之和，每件只计一次；基础结构没有独立价格，不添加隐藏费用。试换模块不重复扣款，装卸、碰撞和补能不产生金钱奖惩，预算不是跨局钱包。
4. R = B − C；要求 0 ≤ C ≤ B。刚好用满预算可以开局，超预算不能开局。负数、非有限价格/预算属于无效数据，不能用截断修正获得成绩。
5. 开局冻结 missionId、difficulty、rulesVersion、任务定义、配置、budget、configurationCost、remainingBudget 和测试标记；结算使用快照，不读后来改动的选项或目录价格。
6. 驾驶中不更换难度/配置；返回组装或切换模式结束当前局。重试保留难度与配置、重建干净会话；不得继承货物、目标进度或旧分数。

### S9.4 得分前提与公式

正式得分必须同时满足：正常模式、开局配置与预算合法、全部指定货物已交付、完成交付后再次抵达/越过100m终点、当前步无硬失败、该局尚未结算。

先到过终点再回头交货，必须再次抵达终点，不能永久沿用旧 reach 完成记录。只交齐货未到终点、只到终点未交齐，均继续运行并提示缺少步骤。同一步硬失败优先于成功；结果一旦产生就冻结，重复交互不得重复记分。

首版建议公式：

~~~text
不满足得分条件：score = 0
满足得分条件：
  remainingBudget = budget - configurationCost
  difficultyScore = 1000 * D
  budgetBonus = floor(500 * remainingBudget / budget)
  score = difficultyScore + budgetBonus
~~~

按剩余预算占比计算奖励，避免简单档因初始预算多而天然压过困难档。难度基础分1000/2000/3000，预算奖励上限500；同档越省钱分越高（按整数向下取整，微小差额可能同分），通关困难始终高于普通、普通高于简单。D只用于评分，不暗改物理或工具能力。

示例：成本370的合法配置若真实通关，简单剩余230、得1191分；普通剩余130、得2130分；困难剩余80、得3088分。用满预算分别得1000/2000/3000分。示例是公式演算，不是新任务通关证据。

失败或退出正式得分0，反馈未完成目标与失败原因，不给部分完成分。用时、能源、碰撞可作过程统计，首版不加分；旧星标分、货物拾取分、时间奖励不得叠加进新总分。

### S9.5 测试模式、结算和成绩

- 测试模式保留免成本与放开限制，但不得借成本归零得到满额预算奖励。结算显示“测试模式，不计正式成绩”，formalScore 为 null，不写正式最高分。
- 测试通关仍需真实完成目标并到达终点。切回正常模式必须新开局，使用过扶正、无限能源等帮助的会话不能转换成正式成绩。
- 正常结算展示：成功/失败、难度、目标完成情况、预算、成本、剩余预算、难度基础分、节省奖励、总分。手机保持稳定布局，不恢复倾角状态行。
- 成绩按 missionId + difficulty + rulesVersion 隔离保存，记录最高分及对应预算/配置快照；同分保留原记录，不暗加速度排名。刷新和重试不能重复累计分数。
- 正常/测试草稿继续隔离，旧样板与 Phaser 星级不自动换算为新分数；版本化成绩不得覆盖现有配置草稿，损坏记录安全忽略。
- 当前成绩属于静态站点的本地记录，本轮不包含联网排行榜或服务端防作弊。

## S10. 能源、零件定价与环境交互（2026-10-18，当前快照已部署，后续开发暂停）

### S10.1 问题依据、目标与边界

用户反馈的核心问题是“配置没有形成取舍”，不能仅通过整体提高耗电或继续压缩预算解决。本节定义 challenge-v2 的开发目标；具体金额、容量、地形尺寸、能耗与时间均为首轮调参候选，不是已验证平衡值，也不是用户指定数值。发布前按 S10.10 实测、修订并冻结。

当前依据来自 src/data/modules.ts、src/content/preview.ts、src/content/challenges.ts、src/domain/simulation/driving.ts 及 S9.7 的既有报告：

- 简单轮式剩余71.39、普通轮式剩余67.88，但困难履带仅剩9.92；均使用80容量小电池且沿途有两次20单位补给。能源冗余并非所有配置一致，不能统一乘耗电倍率。
- 现行100容量上限把150/250容量电池排除，导致三档电池实际只剩小电池可选。困难首轮静态检查仅4套合法配置，四足超预算；这反映价格、质量、能力与容量限制的叠加。
- 现行驾驶以底盘/电机固定耗电、距离、质量和坡度计算；尚没有本节要求的土质、打滑、工具作业、传感辅助等完整交互。旧目录中的 power、efficiency、energyConsumption 等字段不能直接视作已进入新驾驶模型。
- 困难20kg单件需要机械臂，推土铲与机械臂又占用同一工具槽。若直接加入必需清障任务，会重新产生互斥装备问题。

设计目标：省钱方案可以靠选路和操作通关；花钱购买合适能力可以减少空转、绕路、重复装卸或失稳。昂贵配置不保证更高分，便宜配置也不应在所有地形上无代价占优。障碍服务于既定运输任务，不另加随机任务、强制收集或付费消耗品。

继续保留手动驾驶、三档自由选择、固定货物与交付位置、分批运输、失败优先、交付后再次到达终点、测试成绩隔离。新增辅助只调节玩家输入下的限速/姿态与提示，不自动行驶或替玩家选路。

基础质量仍20kg，干质量上限由80调整为90kg，电池容量上限仍100（新三档容量均可用）。90kg是本项目候选结构限制，不代表任意真实机器人额定载荷；不得只改校验而忽略接触力、制动、重心和翻倒响应。货物质量不计入干质量上限，但始终计入行驶总质量，并受搬运工具累计载重约束。推土铲没有运输载重额度，不把旧 payload=15 当成可运输15kg。

困难档仍必须能单独搬运20kg重货，当前只有机械臂满足；本轮不为了增加数量而让18kg抓取器越额搬货。困难配置多样性重点来自底盘、电机、电池、感知和附件，简单/普通同时覆盖两种搬运工具。未来新增重载抓取器须另立型号与价格。

C 为所有已装模块（含附件）的目录价格之和，空附件为0；计价、干质量、配置快照与重心使用同一份配置。沿途不能拆卖/换装，不新增购买电量或修理扣款。

### S10.3 环境、能力与合理代价

下表是待开发的交互合同，优势必须来自可解释的接触、作业或辅助过程，不能按模块 ID 直接赠送一段能源。

| 环境/障碍 | 适配零件如何发挥作用 | 未适配时的可行选择与代价 | 能力边界 |
|---|---|---|---|
| 平整硬地 | 轮式以较小行驶损耗通过，低功耗电机轻载工作 | 履带多出履带运动损耗，四足承担摆腿与支撑功耗 | 四足不能在所有地面都最省能 |

| 路缘/错落路面窄段 | 深度相机提供近场间隙/落脚辅助；雷达提前测距提示减速 | 摄像头仍可看见障碍，玩家可提前慢行；失误会造成制动、再加速或接触损耗 | 感知不改变摩擦或电机效率，不隐藏障碍强迫买传感器；雷达不透视 |

软土至少区分接地面积、沉陷阻力与滑移；碎石/台阶至少区分高度、间距、接触与离地间隙；坡路明确坡度、表面牵引与总质量。参数是游戏中的简化模型，不能将其宣传为完整土力学或工程仿真。

传感器能力依据环境几何和实际可见范围启用。首轮辅助距离：摄像头可见目标提示5m、深度相机近场几何8m、雷达前向几何15m；均受遮挡和视场约束，越界不得提供精确脚点。雷达不能完全替代深度相机的近场落脚辅助。辅助可关闭，关闭后物理不变；完美手动操作允许达到相近能耗，不能为了卖传感器强行惩罚玩家。不得用随机失控证明高级传感器有价值。

### S10.4 统一能量账本与电池取舍

1 能量单位 EU 暂映射为100J的游戏计量尺度，仅用于统一工作、损耗与功率的量纲；UI 显示能量或百分比，不标成真实 Wh，也不宣称电池密度对应实际产品。首版以一次满电出发，容量45/70/100 EU；满电即容量，不再叠加隐形基础能源。

每步耗能由同一账本汇总：

- 驱动机械正功：克服滚动/沉陷阻力、爬升、正向加速；使用实际路径距离、坡高与实时整机加货物质量。驱动端正功除以相应负载区间效率得到电能。
- 滑移与堵转损耗：滑移使用接触切向力与滑移速度；无位移时不能按距离计功，但仍可能存在电机电损耗。电流/功率受限，连续堵转1秒触发降功率保护；松开油门可停止驱动耗能，不能在路障上无限满功率自动冲击。
- 四足执行：按支撑/摆腿/姿态修正计算执行器电能代理，代替轮履驱动项，不能叠加第二份固定驾驶耗电。脚端正功、摆腿周期和支撑保持损耗分项记录，禁止仅按“装备四足”给通过障碍打折。
- 系统与感知：首轮基础电子功率6W，摄像头2W、深度相机5W、雷达8W。传感器辅助关闭不等于断电；若增加断电开关，必须同时关闭感知输出。运行中停车仍耗电；暂停、组装、结束后不耗电。
- 工具/附件：抬升按实际负载及高度、推移按阻力及距离，加执行器损耗；停稳装卸、清障分别记录耗能。运输中载荷放在明确的固定托架上，移动质量与重心仍保留，工具不可无条件重复收取整段举升能量。托架只承接当前搬运工具的载重额度，不提供免费的独立搬运能力。

相同机械功只能入账一次：若驱动已经用接触力积分，不再另加同一段坡度/距离扣电；若沿用简化功代理，就不能再全量叠加旧 driveDrain、drainUnitsPerM 与 gradeResistanceFactor。制动不回充，重力下坡不产生负耗能，碰撞不能创造能量；损失的动能只在随后再加速时由驱动补回，不重复扣同一笔“碰撞罚电”。

电机使用连续牵引力/功率上限和负载效率曲线，低功耗不是全负载最省电，高性能也不是永远固定更耗电。首轮须标定至少轻载硬地、满载硬地、满载坡路三个工作点，公开到调参表；未标定前不把旧 motor.power 当作已换算的瓦数。电池供电能力与电机共同限制输出，容量只决定储能，不额外赠送速度。

清理的障碍状态在该局内保留，返程经过已清通道只付行驶能耗。软土每次实际行驶都产生阻力；静止在区域中不重复收取“进入费”。每步先算能量需求，再按剩余电量限制可执行的工作/运动，不能用最后一点电完成整段清障或瞬移到终点。耗尽后的失败判定仍优先于成功。

### S10.7 能源与多样性验收目标

验收使用正常模式、固定输入记录、完整任务循环。有效供能 = 开局电量 + 实际补给到账；消耗率 = 全局实际耗能 / 有效供能。不得用补给站标称10 EU代替实际到账量，或把过充浪费算成已用能源。

- 参考方案能源目标：简单轻量消耗60%–80%；普通适配方案消耗70%–90%；困难适配的标准电池方案消耗80%–95%。这些是调参区间，允许优秀操作及不同容量偏离；大电池有明显余量属于花钱购买容错，不应强行把所有方案终点电量拉平。困难不得以接近0的单帧极限操作作为唯一通法。
- 保底多样性：每档至少6套完整正常模式通关配置；困难覆盖轮式、履带、四足各至少2套，且同底盘两套至少在电机、电池或附件之一不同，不能只换传感器凑数。全体通关配置至少覆盖两档电机、两档电池及有/无附件路线；简单和普通各覆盖机械臂、抓取器。
- 成本可选性：困难至少2套实际通关配置成本不超过360，且其中至少1套不依赖补给。小电池至少有简单和普通的实测通法；标准电池在困难有实测通法；大电池要能安装并真实完成一条正式任务。不得为满足覆盖率破坏能力边界。
- 障碍收益：在适配障碍的成对对照中，至少3类交互使该段总能耗降低20%以上，或使本来物理不可直通的车辆改走可行短路；包含绕行、工具操作、驻留、传感耗电和额外模块质量。不能把旁路能耗排除后宣称节能。该指标是待验证目标，不是写死的减耗倍率。
- 全局取舍：对比清障的首趟投入与往返收益、轮式硬地与履带软地、四足台阶与平地、低功耗轻载与高性能重载。至少形成3类不同有效策略；便宜万能配装若能在所有环境高余量直行，应继续调参，而非用装备黑名单修补。
- 感知价值单独验收：使用一致的玩家反应延迟与意图脚本，对比开启/关闭近场或远场辅助的接触次数、再加速能耗、失稳次数。可允许省能不足20%但风险降低；另用熟练手动脚本证明摄像头可以安全通行，不要求雷达在任何场景都胜出。
- 容错：每档至少一套参考方案能承受一次额外停车再启动与3秒运行中等待后仍通关；不承诺故意撞击、长时间空转或乱走路线也可完成。时限、能源、倒地失败都必须能真实触发。

报告按配置记录：版本、成本、干质量、容量、货物与路线、总里程、耗时、补给实收、驱动/感知/工具分项能耗、最低及最终能源、接触/失稳/失败原因、正式分数。未完成任务的方案只记录失败与0分，不能只展示终点电量。

### S10.8 得分、存档与测试模式

评分公式继续使用 S9：成功得1000 × D + floor(500 × (B − C) / B)，失败/退出0，测试 formalScore=null。能量、时间与传感器档位不额外加分；省能的价值在于完成任务和省下设备预算。正式成功仍要求全部指定货物有效交付后再抵达终点，同步硬失败优先。

价格、容量、能耗、质量上限、槽位和路线变化使用新规则版本 challenge-v2；v1 最佳成绩保留并标版本，不混合排名，也不把旧配置按新低价重新算高分。开局快照新增目录版本及实际参数、路径/障碍定义、能量模型参数、工具附件与容量；运行和结算都读同一冻结快照。

迁移边界：只保留上次选择的难度与可识别配置 ID；将旧 blade 工具迁入附件槽时，必需搬运工具留空并提示补选，不静默赠送机械臂。其他装配重新校验成本/质量/能力；旧进行中会话不得跨规则恢复，提示规则更新后重新开始；历史成绩只读。重试重置碎料、清障、补给、货物和能量账本。

测试模式保留免费组装/能源豁免与已有测试便利，不进入正常模式验收或正式记录。内部可增加“按正常规则预估耗能”的只读调试账本，必须与实际不扣电状态明确区分；不得把它包装成真实剩余电量。两种模式的状态和成绩存储持续隔离。

### S11.3 障碍必须有可理解的实体表现

1. **台阶优先。** 将当前两个隆起踏段表现为可辨认的阶面、边缘、侧面和高度阴影；普通/困难分别以当前0.08m/0.16m高度为首轮基准，不把尺度夸大成实际不存在的高墙。简单档 severity=0 的“细碎石”继续表现为低矮碎石，不显示为大台阶。
2. 当前台阶接触面使用0.9m平滑过渡，不得只加陡直装饰立面却让机器人穿面。可用贴合接触轮廓的斜缘/倒角凸显踏面；若改为更陡的真实阶形，须同步修改接触采样、通过能力与能源模型，并重新验证三种底盘。道路顶面、侧裙和底层地面必须避免重叠闪烁、悬浮及背面缺失。
3. 软土以泥面凹凸与车辙区分；窄段须有连续可见的边界和宽度参照；碎料有真实体积及清理前后状态；坡路展示连续高差；充电支路和障碍旁路使用不同服务标识。按本次困难布局移除的障碍也须从显示与碰撞中一起移除。
4. 地形高度、障碍范围、足轮接触、道路边界和可通过性使用共同数据。视觉轮廓可以简化，但不得出现“看似平地却被挡住”“脚踩空中”“显示已清理仍被挡”或只换贴图掩盖接触问题。
5. 以实际游玩相机验证，而不只检查近景编辑视角：桌面、手机竖屏、正向进入和倒车返回都能认出阶面；借助材质明暗与轮廓识别，不依赖一串浮动文字。相机调整须平滑，障碍/路线/机器人不能被 HUD 遮住。

| 可选路 | 独立突出的“直行 / 走旁路”按钮组，明确当前选择 | 初始直行照常标明；保留入口/返程路口的安全提交规则（当前端点外2m内且速度不超过0.75m/s）。超速时短提示“减速选路”；不能自动刹车或偷换路线 |
| 已入分支 | 持续显示“已选旁路”或“已选直行” | 当前路线沿途箭头/边线明确，选中与禁用态分开。禁止在分支中途切路导致瞬移；暂停、清障等状态不覆盖当前路线确认 |
| 汇回主路 | 短暂“已汇入主路”后恢复常规状态 | 曲线、路面、朝向连续汇入；返程同样可辨认并可在合法路口重新选择 |

实施要求：

- 选路组从五个等权小按钮中独立出来，与驾驶输入同时可见；可点区域至少44×44 CSS px，选中状态同时使用短文字/图标和样式，不只靠颜色。竖屏使用预留固定区域，提示长短与按钮可用性变化不能让画面上下跳动。
- 道路须有可辨认的分岔口、足够的路肩或间隔、沿曲线布置的方向箭头、旁路边线及汇入口。障碍位于直行区域，充电支路标服务图标；相邻支路不能画成重叠、断开的假路。
- 已选路线使用连续强调，另一条路线保留可辨轮廓；选择变化须在界面和场景同步。标线按照真实路线切线旋转，不把横向小方块当作完整路径表现。
- 相机根据当前曲线路径与机体位置平滑跟随，竖屏能看到机器人及近期路段、入/汇口；必要时平滑调整取景，禁止仅沿 x 跟踪导致旁路移出屏幕，禁止瞬间跳镜头。
- 旁路额外距离、实际移动距离和计时/能量消耗共用路线数据。基础障碍名与路线标识不等于高级感知辅助，感知收益继续由预警范围、居中与风险体现。

### S11.6 四足沿曲线行走、转向与接触

**必须改进运动和接触坐标处理，不能只给整机加一个旋转动画。** 采用共享路线坐标：路径参数决定世界位置，切线决定行进基准朝向，弧长决定实际速度/步态推进。轮式、履带和四足均引用同一份路径定义。

1. 将当前按 lane 差值平移机身和所有足端的方式替换为连续的路径跟随与转向目标。路径基准朝向与刚体平衡姿态正确组合，保留真实俯仰、侧倾、重心及翻倒状态；不能覆盖物理姿态来伪装转弯。
2. 支撑脚在世界地面保持接触位置，除模型允许且可测的真实打滑外不得随机身横向搬移。摆动脚依据未来机体位置和路线切线落脚，内外侧脚允许不同步幅，步态节奏随实际路径速度推进，停下时不继续踏步。
3. 接触点、地面法向、力矩、摩擦和足端目标使用同一坐标变换；转弯时载重重心和惯性仍参与稳定性计算。既有失稳/翻倒不能被路径位置重置“扶正”；必要的受约束运动须在物理状态内一致处理并如实说明模型边界。
4. 进入、弯中和汇入都要连续，机身不得横向瞬移或朝向突跳；制动时按实际速度减速。倒车沿已选路线退行，机头保持与底盘前向一致，不能因为速度变负而瞬间掉头180°；反向步态和履带/车轮旋转同步。
5. 路径弧长积分、实际行程、速度换算和能量账本一致，须包含高度变化；不能把 x 方向位移直接当成四足完整运动距离。暂停/恢复、重试、清障、载货/卸货和空电量均不得留下姿态或足端坐标偏差。
6. 允许继续使用游戏级路径约束和简化接触模型，但必须展示连续转弯、合理支撑和载重反应；不宣称实现全三维自由驾驶或完整关节执行器仿真。

- 这三处按“载重通行—越障—清理或绕行”形成不同决策；两次运输会自然复用路段，不能再靠增加强制障碍补难度。移除路段的旧旁路、标签、预警、碰撞与环境成本同步清除。
- 预算450、20kg+8kg货物、装卸区、终点100m和180秒时限先保持，装载/交付平台的平整、安全停靠条件必须保留。困难仍来自预算和重货往返，不强制购买前铲、最大电池或高级传感器。
- 三件碎料为首轮标定值；前铲应体现批量效率，没有前铲仍可用合规机械臂或旁路解决，必须遵守现有载荷和净空。收益须用实际时间、能耗及装配成本比较，不通过虚构工具用途制造优势。
- 重新验证全程后才确定最终难度。若过于轻松或某底盘仍无合理选择，优先调整这三处的局部参数、旁路代价或碎料工作量，并回写依据；不恢复障碍堆叠，也不暗中上调价格/削减电池或预算。
- 困难布局、基础地形或能耗/通过能力发生实质变化时，挑战规则升级为 challenge-v3；环境版本按数据兼容性另行决定。v2 成绩保留原版本标识，v3 独立比较，不能把旧成绩直接当成新布局记录。测试模式仍不写正式排行榜。

## 1. 问题 1：油门/刹车按钮失灵

### 1.1 根因定位

#### Bug A（主因）：按钮容器与子对象的 scrollFactor 不一致

位置：`src/scenes/MissionPlayScene.ts:287-291`

```ts
const container = this.add.container(x, y).setScrollFactor(0);   // 只设置了容器
const bg = this.add.circle(0, 0, size / 2, color, 0.3);
bg.setInteractive({ useHandCursor: true });                      // 交互对象是 bg，scrollFactor 仍为 1
```

机理：

1. Phaser 渲染容器时使用**容器自身**的 scrollFactor（0），所以按钮看起来固定在屏幕上。
2. 但输入命中检测（`node_modules/phaser/src/input/InputManager.js:924-925`）使用的是**交互对象自身**的 scrollFactor：
   ```js
   var px = tempPoint.x + (csx * gameObject.scrollFactorX) - csx;
   ```
   `bg.scrollFactorX = 1`，因此命中区域会跟随相机滚动。
3. 相机 `startFollow(robotSprite)` 后，机器人一开动相机就滚动 → **按钮的可点击区域被移出屏幕**。
4. 同时因为命中区域在移动，即使手指没动，也会触发 `pointerout`，把 `accelerate` 置 false。

表现完全吻合 ISSUES 描述：**开局能用，车跑起来后时灵时不灵**，移动端（长按）尤其明显。

#### Bug B：场景重入时状态未重置

位置：`MissionPlayScene.ts:19, 41, 44-46, 65-73`

Phaser 的 `scene.start()` 复用同一个 Scene 实例，**类字段初始化器不会再次执行**，只会重新调用 `create()`。而 `create()` 只重置了位置/速度/能源等，没有重置：

| 字段 | 上一局结束后的值 | 后果 |
|---|---|---|
| `isPlaying` | false | 无影响（会被 startMission 置 true） |
| `missionComplete` / `missionFailed` | **true** | `update()` 第一行直接 return → **整局无响应** |
| `drivingInput` | 可能残留 true | 一开局就自动加速/刹车 |
| `items` | 包含上一局已销毁的对象 | 对已销毁对象做距离检测和 tween，产生异常 |

复现：完成或失败一局 → 点"重新配置" → 再"开始任务" → 按钮和键盘都无效。

#### Bug C：键盘与虚拟按钮共用同一个状态位

位置：`MissionPlayScene.ts:302-327`、`332-355`

- 按住虚拟油门的同时按/松 W 键，松开 W 会把 `accelerate` 清零，虽然手指还按着。
- 浏览器窗口失焦（切换标签、弹出系统通知）时收不到 `keyup`，状态卡死为 true。
- 只用 `pointerup` / `pointerout`，没有处理 `pointerupoutside`、触摸被系统取消等情况。
- `main.ts` 未配置 `input.activePointers`，默认只有 1 个触点，**移动端无法同时按油门和刹车**，第二根手指的事件会被丢弃或抢占。

#### 步骤 2：输入系统重构（约 2–3 小时）

新建 `src/systems/InputController.ts`，职责：**把多个输入源分别记录，最后合成驾驶意图**。

```ts

  brake: boolean;
  tiltLeft: boolean;   // 为第 5 章物理预留（空中调姿）
  tiltRight: boolean;
}

type Source = 'keyboard' | 'touch';

export class InputController {
  private state: Record<Source, DrivingIntent>;
  private buttons: { action: keyof DrivingIntent; rect: Phaser.Geom.Rectangle }[] = [];

  constructor(private scene: Phaser.Scene) {
    // 1. 键盘：使用 addKeys 而不是 keydown 事件，每帧读取 isDown，天然不会"卡键"
    // 2. 失焦：scene.game.events.on(Phaser.Core.Events.BLUR, this.clearAll)
    // 3. 场景 shutdown 时自动解绑
  }

  /** 注册一个虚拟按钮的屏幕区域（屏幕坐标，含容错外扩） */
  registerButton(action: keyof DrivingIntent, x: number, y: number, radius: number, padding = 0.2) { }

    // 触摸：遍历 scene.input.manager.pointers，
    //        对每个 isDown 的 pointer 取 (pointer.x, pointer.y)（屏幕坐标），
    //        判断落在哪个按钮的 rect 内 → 置对应 action 为 true
```

| 要点 | 说明 |
|---|---|
| **轮询而非事件** | 每帧根据"当前有哪些手指按在哪里"计算状态，不依赖 down/up/out 事件的配对，从根本上消除状态错乱 |

| **容错范围** | 判定半径 = 视觉半径 × 1.2，手指轻微滑出不会断 |
| **滑动切换** | 手指从刹车滑到油门，自然切换（轮询天然支持） |
| **按钮视觉** | 按钮只负责显示，由 `poll()` 结果驱动按下/抬起外观 |

## 3. 问题 2：装备参数未生效

### 3.1 总体设计：RuntimeParams 换算层

问题本质：模块数据（`modules.ts`）与玩法代码（`MissionPlayScene.ts`）之间**缺少一层"参数 → 玩法数值"的映射**，导致很多字段写了但没人读。

新建 `src/systems/RuntimeParams.ts`：

```ts
export interface RuntimeParams {
  // —— 动力（底盘 + 电机 + 质量）——
  mass: number;               // 总质量 = 机身 + 模块 + 货物
  accel: number;              // 加速度 px/s²
  maxSpeed: number;           // 最高速度 px/s
  brakeDecel: number;         // 刹车减速度 px/s²

  // —— 能耗 ——
  drainPerSec: number;        // 加速时每秒耗能
  idleDrainPerSec: number;    // 待机耗能（传感器、工具常开）

  // —— 感知 ——
  pickupRadius: number;       // 道具拾取半径 px
  revealDistance: number;     // 障碍物"看清"距离 px
  warnDistance: number;       // 碰撞预警距离 px
  warnDelay: number;          // 预警延迟 s（精度越低越晚）

  // —— 稳定性 ——
  controlSpeed: number;       // 可控速度上限，超过后失控风险增加
  collisionDamageMul: number; // 碰撞能源损失倍率
  maxTiltDeg: number;         // 最大可承受倾角（第 5 章使用）

  // —— 负载 / 工具 ——
  payloadCapacity: number;    // 可承载货物重量 kg
  toolCapability: 'transport' | 'clear' | 'grab' | null;
}

export function buildRuntimeParams(
  config: RobotConfig,
  mission: MissionData,
  cargoWeight = 0,
): RuntimeParams { /* 见下方公式 */ }
```

使用方式：

- `create()` 中计算一次并缓存为 `this.params`
- 拾取/放下货物时（质量变化）重新计算一次
- `MissionExecutor`（自动模拟）也改用同一个函数，保证两边结果一致

### 3.2 各参数的玩法映射与公式建议

> 下列系数是**起始建议值**，目标是让现有 5 个任务在"合理配置"下仍可完成，具体以实测调参为准。

#### 3.2.1 电机效率 / 动力（ISSUES 2.5）

现状：`MissionPlayScene.ts:477-489` 能耗 = Σ模块能耗 × 重量系数 × 2，未使用 `efficiency` 和 `power`。

```
terrainMod  = 底盘 terrainMultiplier[地形]               （现有逻辑）
massFactor  = clamp(70 / mass, 0.6, 1.3)                 （越重越慢）
accel       = stats.speed × 50 × motor.power × terrainMod × massFactor
maxSpeed    = stats.speed × 100 × terrainMod
drainPerSec = Σ动力模块能耗 × weightFactor × (2 − terrainMod 截断到 [0.5,1.5]) ÷ motor.efficiency × 1.4
```

说明：

- 系数 `1.4 = 2 × 0.7`：在地形因子为 1 时，标准电机（效率 0.7）的能耗与现在一致，避免整体平衡被打乱；加入地形因子后，优势地形更省电、劣势地形更费电，需要随第 6 章任务一起复调。
- 低功耗电机：能耗约为现在的 78%；高性能电机：约为 140%。
- 地形因子与 `MissionExecutor.ts:179` 保持一致。

#### 3.2.2 传感器 / 感知（ISSUES 2.1）

| 字段 | 玩法 | 公式建议 | 摄像头 / 深度 / LiDAR |
|---|---|---|---|
| `perception` | 道具拾取半径 | `30 + perception × 0.4` | 46 / 58 / 68 px |
| `range` | 障碍物显形距离：超出距离的障碍只显示灰色"?"剪影，进入后显示真实类型 | `range × 40` px（玩法尺度，非真实米） | 200 / 320 / 600 px |
| `accuracy` | 预警：障碍进入 `warnDistance` 时屏幕边缘闪红 + 提示音；精度低则预警晚 | `warnDistance = revealDistance × accuracy`；`warnDelay = (1 − accuracy) × 0.8s` | 120/256/570 px；0.32/0.16/0.04 s |
| `energyConsumption` | 传感器常开耗能（即使不踩油门） | 计入 `idleDrainPerSec` | — |

效果：LiDAR 能更早看清前方是"可推的木箱"还是"必须减速的石头"，从而提前决策。

#### 3.2.3 稳定性（ISSUES 2.2）

| 玩法 | 公式建议 |
|---|---|
| 可控速度 | `controlSpeed = maxSpeed × (0.5 + stability / 200)`，轮式(50+30基础)=0.9，履带≈1.05 |
| 超速失控 | 速度 > `controlSpeed` 时：车身抖动（视觉），每秒有 `(v/controlSpeed − 1) × 0.5` 概率"打滑"，速度损失 20% |
| 碰撞伤害 | `collisionDamageMul = 1.5 − stability / 100`，单次碰撞耗能 = 5 × 该倍率 |
| 崎岖地形 | 颠簸幅度 ∝ `(100 − stability)`，第 5 章物理中作为悬挂阻尼的加成 |
| 翻车阈值 | `maxTiltDeg = 45 + stability × 0.4`（第 5 章使用） |
| 货物掉落 | 碰撞时有 `(1 − stability/100) × 0.5` 概率掉落一件货物 |

#### 3.2.4 负载（ISSUES 2.3）

1. 货物道具带 `weight` 属性（轻货 8kg、重货 20kg、小零件 2kg）。
2. 拾取判定：`当前载货重量 + 货物重量 ≤ payloadCapacity`，否则显示"负载不足"浮字，不可拾取。
3. 拾取后货物重量计入 `mass`，重新计算 `RuntimeParams` → 加速变慢、能耗变高。
4. 货物显示在机器人车斗/机械臂上（美术见第 10 章）。
5. 到达卸货区（`zone_delivery`）后自动卸货，计入运输目标进度。

#### 3.2.5 工具差异化（ISSUES 2.4）

用"工具能力 × 物品类型"矩阵统一判定，新建 `src/data/interactionRules.ts`：

### 5.2 地形：高度场

### 5.3 车辆：射线悬挂模型

新建 `src/physics/VehicleSim.ts`（纯逻辑，不依赖 Phaser，便于单元测试）：

```ts
interface VehicleState {
  x: number; y: number;        // 车身质心
  vx: number; vy: number;
  angle: number; angVel: number;
}

interface WheelDef { offsetX: number; restLength: number; radius: number; driven: boolean; }

export class VehicleSim {
  constructor(params: RuntimeParams, wheels: WheelDef[], terrain: Terrain) {}
  step(intent: DrivingIntent, dt: number): StepEvents;
}
```

每个物理步（固定步长 1/120 s，在 `update()` 中累加 delta 分步执行）：

```text
1. 对每个车轮：
   a. 计算车轮挂点的世界坐标（受车身 angle 影响）
   b. 竖直向下"射线"：groundY = terrain.heightAt(wheelX)
   c. 压缩量 c = restLength − (groundY − anchorY − radius)
   d. 若 c > 0（着地）：
        弹簧力 F = k × c − d × (dc/dt)
        累加到车身：线力 + 力矩（力 × 挂点到质心的水平距离）
        若 driven 且 accelerate 且有能源：沿地面切线施加驱动力 accel × mass / 驱动轮数
        若 brake：沿切线施加反向制动力
2. 重力：vy += g × dt
3. 空中调姿：未着地时，tiltLeft/Right 施加 ±adjustTorque（参考.md §4 步骤 1）
4. 软限速阻尼：沿用 参考.md §4 步骤 4 的公式（当前代码 :440 已有）
5. 积分：半隐式欧拉
6. 输出事件：着地/腾空、颠簸强度、是否翻车
```

### 5.4 三种底盘的差异化

| 底盘 | 车轮配置 | 悬挂刚度 k | 阻尼 d | 特点 |
|---|---|---|---|---|
| 轮式 | 2 轮，后轮驱动，半径 12 | 中 | 低 | 平地快，崎岖地形弹跳明显 |
| 履带 | 5 个小负重轮全驱，半径 8，高摩擦 | 高 | 高 | 贴地稳，过坎平顺 |
| 四足 | 4 个虚拟"足点"，长行程悬挂，配合步行动画 | 低 | 很高 | 崎岖地形几乎不颠簸 |

稳定性参数在这里体现为：`d_实际 = d_底盘 × (0.6 + stability/100)`，以及 `maxTiltDeg` 翻车判定。

### 5.5 翻车与失败

`MissionPlayScene` 重构后的 `update()` 应接近：

```ts
update(_t: number, delta: number) {
  if (this.phase !== 'PLAYING') return;
  const intent = this.inputCtl.poll();
  const events = this.sim.stepFixed(intent, delta / 1000);   // 物理
  this.items.update(this.sim.state, this.params, this.emit);  // 拾取
  this.obstacles.update(this.sim.state, this.params, this.emit); // 碰撞 / 预警
  this.robotView.sync(this.sim.state, intent, events);        // 显示
  this.audio.setEngineSpeed(this.sim.speedRatio());
  this.hud.update(this.runState, this.objectives);
  const status = this.objectives.status();
  if (status !== 'running') this.finish(status);
}
```

## 13. 测试与验收清单

### 13.1 自动化测试（建议）

项目当前无测试框架。建议引入 `vitest`（与 Vite 同源，零配置），只覆盖**纯逻辑模块**：

| 模块 | 测试内容 |
|---|---|
| `RuntimeParams` | 每个模块切换后对应派生值单调变化（如效率↑ → 能耗↓） |
| `RobotConfig` | `requiredCapability` 匹配正确；任务 3、5 需求可被满足 |
| `ObjectiveSystem` | 各目标类型的完成/失败判定 |
| `VehicleSim` | 平地全油门 N 秒后速度收敛到 maxSpeed 附近；静止放置不会穿地 / 弹飞 |
| `interactionRules` | 矩阵覆盖所有物品 × 能力组合 |
| 平衡测试 | 遍历全部 324 种配置（底盘 3 × 电机 3 × 电池 3 × 传感器 3 × 工具 4〈含无工具〉）× 5 个任务，用 AI 司机跑 `MissionExecutor`，输出通过率表；要求每个任务至少有 3 种以上配置能通过，且不存在"万能配置" |

### 13.2 手动测试

| 场景 | 检查点 |
|---|---|
| 输入 | 见 1.4 |
| 重开 | 成功/失败后 → 重新配置 → 再开始，状态完全干净 |
| 装备 | 见 3.4 |
| 工具 | 任务 3 无抓取器无法通过；任务 5 无机械臂无法通过；推土铲清除木箱不计碰撞 |
| 物理 | 三种底盘过崎岖地形的颠簸程度明显不同；翻车判定生效 |
| 结算 | 失败界面显示具体原因 + 建议 |
| 移动端 | Chrome DevTools 设备模拟 + 至少一台真机（iOS Safari / Android Chrome） |
| 性能 | 最长关卡（任务 05）在中端手机上 ≥ 50 FPS |
