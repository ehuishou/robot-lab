# Robot Lab 游戏开发框架 V0.1

> **项目定位：** 一款网页端 + Android 端的机器人设计挑战游戏。玩家在能源、重量、预算和任务特殊规则的约束下搭配机器人模块，让机器人自动执行任务，并根据执行结果不断重新设计。
>
> **核心不是机器人升级，而是机器人设计。**

---

## 1. 项目一句话定义

玩家接受任务 → 分析约束 → 组装机器人 → 自动执行 → 获得反馈 → 分析失败/表现 → 修改配置 → 再次执行。

核心循环：

```text
任务
 ↓
分析限制
 ↓
组装机器人
 ↓
执行任务
 ↓
成功 / 部分成功 / 失败
 ↓
分析原因
 ↓
修改机器人
 └────────→ 再次执行
```

---

# 2. 核心设计原则

## 2.1 不是升级游戏，而是设计游戏

本项目不以传统 RPG 等级、稀有度和数值膨胀作为主要成长方式。

玩家获得的不是越来越强的固定机器人，而是越来越多的设计选择。

## 2.2 所有配件必须有优势与代价

例如：

| 配件 | 优势 | 代价 |
|---|---|---|
| 高速电机 | 速度高 | 能耗高、重量增加 |
| 大电池 | 续航高 | 重量增加 |
| 履带 | 越障、稳定 | 速度下降、能耗增加 |
| LiDAR | 感知强 | 成本、重量、能耗增加 |
| 机械臂 | 可以搬运 | 重量、能耗增加 |

不能出现一个模块在所有情况下都明显优于其他模块。

## 2.3 任务变化比装备升级更重要

不同任务应该迫使玩家重新思考配置。

> 不是“装备越来越强”，而是“问题越来越不同”。

## 2.4 失败必须产生知识

不能只显示：

> 任务失败。

必须告诉玩家：

- 什么原因导致失败；
- 在什么时候发生；
- 哪个参数成为瓶颈；
- 哪些配置方向可能改善结果。

## 2.5 玩家最终获得的是“解决问题”的成就感

核心奖励不是金币、等级或稀有装备，而是：

> “我自己设计出了一个能完成任务的机器人。”

# 4. 核心用户

第一批目标用户：

- 喜欢机器人、机械、工程的玩家；
- 喜欢策略、模拟、优化类游戏的玩家；
- 对机器人有兴趣但没有专业编程/机器人知识的普通玩家。

不要第一版就面向专业机器人研究人员。

目标是：

> **让普通玩家产生“我在设计机器人”的感觉，而不是要求玩家真的掌握机器人学。**

---

# 5. 核心玩法

## 5.1 玩家角色

玩家不是直接驾驶机器人。

玩家是：

> **机器人设计师 / 工程师。**

设计阶段玩家进行决策；执行阶段玩家观察机器人自主完成任务。

---

# 6. 机器人系统

机器人由以下模块组成：

```text
机器人
│
├── 底盘
├── 移动系统
├── 能源系统
├── 感知系统
├── 功能模块
└── 辅助模块
```

## 6.1 核心参数

第一版只使用 7 个核心参数：

```text
Weight       重量
Energy       能源容量
Speed        速度
Stability    稳定性
Payload      负载
Perception   感知
Cost         成本
```

不要第一版就加入十几个参数，避免游戏变成 Excel。

---

# 7. 模块设计

## 7.1 底盘

### 轮式底盘

优势：

- 平地速度高；
- 能耗较低。

劣势：

- 越障能力弱；
- 复杂地形表现差。

### 履带底盘

优势：

- 越障能力强；
- 稳定性高；
- 适合坡地。

劣势：

- 速度较低；
- 能耗较高。

### 四足底盘

优势：

- 复杂地形适应能力强。

劣势：

- 成本高；
- 能耗高；
- 系统复杂。

---

# 8. 动力系统

第一版：

## 低功耗电机

```text
速度：低
效率：高
重量：低
```

## 标准电机

```text
速度：中
效率：中
重量：中
```

## 高性能电机

```text
速度：高
效率：低
重量：高
```

---

# 9. 能源系统

## 小电池

- 轻；
- 容量低；
- 成本低。

## 标准电池

- 综合平衡。

## 大电池

- 容量高；
- 重量高；
- 成本高。

重要系统关系：

```text
大电池
 ↓
机器人变重
 ↓
需要更强动力
 ↓
能耗增加
 ↓
可能又需要更大电池
```

这种相互制约是游戏深度的重要来源。

---

# 10. 感知系统

第一版：

## 摄像头

- 成本低；
- 基础感知能力。

## 深度摄像头

- 感知更强；
- 重量和能耗增加。

## LiDAR

- 感知能力强；
- 成本、重量和能耗较高。

现实参照可采用模块化机器人生态的思路：传感器、电机、机械臂等均作为独立组件进行设计，而不是将机器人作为不可拆分的整体。

---

# 11. 功能模块

第一版：

## 机械臂

用途：

> 搬运、抓取物体。

## 推土铲

用途：

> 清除障碍。

## 抓取器

用途：

> 抓取指定目标。

这些模块不是“属性加成”，而是改变机器人**能做什么**。

---

# 12. 任务系统

任务不是单纯的地图。

任务应该是一组：

> **目标 + 环境 + 约束 + 特殊要求**

例如：

```json
{
  "id": "task_001",
  "name": "仓库搬运",

  "objective": {
    "type": "transport",
    "targetCount": 3
  },

  "environment": {
    "terrain": "flat",
    "obstacles": "medium"
  },

  "constraints": {
    "maxEnergy": 100,
    "maxWeight": 80,
    "maxCost": 500,
    "maxTime": 120
  },

  "requirements": {
    "minPayload": 20,
    "requiredModule": "gripper"
  }
}
```

# 13. 第一批任务

## Task 01：平地运输

目的：

> 教玩家理解重量、能源、速度。

## Task 02：山地运输

加入：

- 坡度；
- 不平地形。

迫使玩家考虑：

- 扭矩；
- 履带；
- 重量；
- 稳定性。

## Task 03：仓库搬运

加入：

- 障碍物；
- 搬运目标；
- 机械臂/抓取器要求。

迫使玩家考虑：

- 感知；
- 负载；
- 功能模块。

## Task 04：狭窄空间

加入：

- 体积限制；
- 狭窄通道；
- 精确移动。

迫使玩家考虑：

- 尺寸；
- 机动性；
- 感知。

## Task 05：综合任务

同时加入：

```text
能源 ≤ 100
重量 ≤ 80kg
成本 ≤ 600
时间 ≤ 90s
必须搬运 3 个物体
碰撞 ≤ 3 次
```

这是第一阶段真正的机器人设计挑战。

# 14. 执行系统

玩家点击：

> 开始任务

之后机器人自动执行。

玩家不直接控制机器人移动。

执行流程：

```text
读取机器人配置
 ↓
读取任务限制
 ↓
进入环境
 ↓
移动
 ↓
感知环境
 ↓
处理障碍
 ↓
执行任务
 ↓
计算能源 / 重量 / 稳定性 / 时间
 ↓
完成或失败
```

玩家的核心操作发生在：

> **机器人执行之前。**

---

# 15. 失败分析系统

失败结果必须提供可操作信息。

示例：

```text
任务失败

主要原因：
能源耗尽

发生时间：
42.6 秒

当时状态：

能源：0
速度：3.2m/s
重量：76kg

分析：

机器人重量较高，
导致动力系统持续高负载运行。

可能解决方向：

① 减少机器人重量
② 更换高效率电机
③ 增加电池容量
④ 更换更低能耗的底盘
```

注意：

> 系统可以给出“可能解决方向”，但不要直接告诉玩家唯一正确配置。

---

# 16. 成功反馈

示例：

```text
MISSION COMPLETE

完成时间：68.4s
剩余能源：21%
机器人重量：67kg
碰撞：1
任务成本：420

────────────────

能源效率：★★★★☆
稳定性：★★★★☆
速度：★★★☆☆
成本效率：★★★★★
```

评分用于反馈，而不是取代任务本身。

---

# 17. 不设计唯一答案

同一个任务应该允许：

- 低成本方案；
- 高性能方案；
- 高稳定方案；
- 极限方案。

只要满足任务目标，都可以成功。

这样玩家探索的是：

> **设计空间**

而不是：

> “找攻略中的标准答案”。

# 18. 核心计算模型

第一版使用简化模型，不追求真实机器人动力学。

## 18.1 总重量

```text
TotalWeight =
BaseWeight +
Σ ModuleWeight
```

## 18.2 总能源

```text
TotalEnergy =
BatteryCapacity
```

## 18.3 速度

```text
Speed =
BaseSpeed
× MotorPower
× TerrainModifier
× WeightModifier
```

## 18.4 能源消耗

```text
EnergyConsumption =
BaseConsumption
× MotorLoad
× TerrainModifier
× SensorConsumption
```

## 18.5 稳定性

```text
Stability =
BaseStability
+ ChassisBonus
+ WeightDistribution
- HeightPenalty
```

# 21. 数据与逻辑分离

模块数据与运行逻辑必须分开。

例如：

```text
ModuleData
```

只保存：

```text
名称
重量
能源消耗
成本
属性
```

而：

```text
ModuleController
```

负责：

> 游戏运行时的实际行为。

这样修改装备参数时，不需要修改核心代码。

# 23. 开发阶段

## Sprint 1：最小闭环

只做：

> 一个机器人 + 一个任务。

机器人：

- 底盘；
- 电机；
- 电池。

任务：

> 从起点移动到终点。

目标：

> 配置不同导致结果不同。

---

## Sprint 2：加入核心参数

加入：

- 能源；
- 重量；
- 速度。

目标：

> 玩家开始主动调整配置。

---

## Sprint 3：加入底盘差异

加入：

- 轮式；
- 履带；
- 四足。

加入：

- 平地；
- 坡道；
- 障碍。

---

## Sprint 4：加入任务能力

加入：

- 机械臂；
- 抓取；
- 搬运。

此时游戏从：

> “机器人移动”

变成：

> **“机器人解决问题”。**

---

## Sprint 5：加入失败分析

必须能够回答：

> “为什么失败？”

---

## Sprint 6：完成 5 个任务

如果完成后核心循环依然成立，再扩大内容。

# 24. MVP 验收标准

## 标准 1

新玩家可以在：

> **2 分钟内理解游戏。**

## 标准 2

玩家第一次失败后，会主动修改配置，而不是直接寻找答案。

## 标准 3

玩家可以理解：

> “为什么我的机器人失败了。”

## 标准 4

同一个任务至少存在：

> **2～3 种合理配置。**

## 标准 5

玩家完成任务后，会主动尝试不同配置。

# 26. 参考《Earn to Die》的部分

真正借鉴的是：

```text
配置
 ↓
执行
 ↓
暴露问题
 ↓
重新配置
 ↓
再次执行
```

不直接复制：

- 僵尸；
- 金币；
- 车辆升级；
- 美术；
- UI；
- 关卡；
- 角色；
- 音效。

核心思想是：

> **保留“配置—行动—反馈”的循环，替换掉具体内容。**

# 27. 结合机器人设计的部分

现实机器人生态可以提供游戏设计参考：

```text
机器人本体
+
电机
+
电池
+
传感器
+
机械臂
+
执行器
+
控制系统
```

游戏将这些现实工程对象抽象成：

> **具有不同能力、成本和代价的可组合模块。**

现实机器人研发中存在大量“针对任务选择硬件”的逻辑，游戏则把这种工程决策压缩成普通玩家可以理解的参数和任务约束。

---

# 28. 最终核心公式

整个游戏可以压缩成：

```text
任务提出约束
      ↓
玩家设计机器人
      ↓
机器人执行
      ↓
系统暴露瓶颈
      ↓
玩家理解瓶颈
      ↓
修改配置
      ↓
再次执行
```

一句话：

> **不是让玩家获得一台越来越强的机器人，而是让玩家越来越会设计机器人。**

---

# 29. 第一阶段真正应该做什么

不要马上制作完整游戏。

第一目标：

> **做一个 5 分钟内可以体验完整循环的机器人实验室原型。**

最低要求：

```text
6 个配件
1 个机器人
1 个任务
3 个核心参数
自动执行
失败分析
重新配置
```

如果这个版本已经让玩家产生：

> “等等，我换这个配件再试一次。”

那么核心玩法值得继续开发。

如果没有产生这种行为，应优先修改玩法，而不是增加剧情、地图、角色和特效。

---

# 30. 给 AI 编程工具的开发原则

如果后续使用 Codex 等 AI 编程工具开发，应始终遵循：

1. **先保证核心循环，再增加内容。**
2. **所有模块数据与代码逻辑分离。**
3. **所有参数必须可配置。**
4. **不要为了真实而引入复杂机器人动力学。**
5. **不要通过等级和数值膨胀解决游戏性问题。**
6. **任务设计优先于装备数量。**
7. **失败反馈必须能帮助玩家进行下一次设计。**
8. **每次开发只增加一个可以验证的系统。**
9. **任何新系统都必须回答：它是否增强“设计—执行—反馈—重设计”循环？**
10. **如果答案是否定的，暂不加入。**

---

## 项目最终定位

> **Robot Lab 不是一个“控制机器人”的游戏，而是一个“设计机器人解决问题”的游戏。**

玩家面对的不是：

> “怎么把机器人练得更强？”

而是：

> **“在这些限制下，我怎样设计出一台能工作的机器人？”**
